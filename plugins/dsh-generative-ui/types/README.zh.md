# `$dsh/*` 类型声明

[English](README.md) | 中文

两个 import map，因为各命令需要不同的目标：

| 文件 | 用于 | 目标 |
| --- | --- | --- |
| `importmap.json` | `genui check`、`genui lint` | 旁边的 `.d.ts` |
| `standalone/importmap.json` | `genui build`、`genui dev` | 生成的 JS stub |

当前的 `genui check` 会解析映射的 `$dsh/*` import，但把它们的导出当作 `any`。它可能对一次合法的泛型能力调用报 TS2347，也可能漏掉一个不存在的导出。类型声明仍然是手工签名核对的事实来源；`check.ts` 独立于 CLI 验证它们与运行时一致。

`build` 与 `dev` 生成的页面周围没有 dsh，因此这些能力确实无法工作——会话、模型与工作区都在 harness 里。stub 让这样的卡片仍然可以*构建*：每次调用都会向控制台警告，并返回正确形状的空值（`""`、`[]`、一个空的异步迭代器），因此 `await` 其中之一的页面会继续运行，而不是因 `undefined` 崩溃。所有不触及 harness 的部分——布局、样式、本地状态——都是真实的；触及的部分则是惰性的。

`standalone/` 由 `scripts/gen-standalone.ts` 生成，该脚本从 `bind()` 枚举导出名，而不是维护第二份手写清单，因此实现中新增的能力不会在 stub 中缺失。它在 `build` 与 `prepare` 之前运行。

这些声明是手写的，而不是从 `src/client/runtime/bindings.ts` 发射：卡片应当看到的是能力表面，而不是能力如何抵达宿主。

`check.ts` 让它们保持诚实——它断言声明的表面与 `bind()` 的返回类型**双向**可赋值，因此比实现更窄的声明（隐藏能力）会和更宽的声明（承诺运行时不会做的事）一样失败。已验证它能同时捕获新增方法与签名变化。因此编辑 `.d.ts` 也意味着编辑 `check.ts` 中的转录；这份重复正是重点，因为从被检查对象派生出来的检查无法验证任何东西。

把 map 指向真实 `.ts` 源文件的做法经过实测后被否决：`paths` 目标会作为程序的一部分被编译，于是实现自身的诊断——它 import 的模块、旁边文件中的错误——会作为卡片上的错误出现，而那是模型看不见也修不了的代码。
